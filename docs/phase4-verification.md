## Compatibility and environment notes

- A reported `/play` failure (`Discord 10062 Unknown interaction`, followed by `40060 Interaction has already been acknowledged`) coincided with two StudyHub bot processes using the same token. After stopping the duplicate, `/play` was changed to defer its reply before member lookup and track resolution. The command router now avoids sending a second error response after these Discord acknowledgement errors. A later `/play` run again had two bot processes; one received `10062` while the other executed the command. The extra bot was stopped before stream testing.
- YouTube search results for `unity alan walker` and `double take` returned audio URLs that answered HTTP 403 on a full GET, even after URL refresh. A bounded 1 MiB `Range` request answered HTTP 206, while an open-ended or full-file range could still answer 403. The Sonata compatibility patch now streams YouTube audio in consecutive 1 MiB ranges and feeds the same WebM demuxer. A local test using Sonata's `AudioStreamer` and a simulated voice connection decoded the `double take` track and emitted 266 Opus frames over 12 seconds without `loadFailed`. A user-run `/play` retest is still pending.
- The first user-run `/play double take` retest started the track, but the sound was choppy. A complete local download of the same track yielded 8,597 Opus packets, zero decoder errors, and 171.94 seconds of decoded audio for a 172-second video. Sonata's own 20 ms packet producer initially left only about one packet queued for the separate Discord 20 ms sender. The compatibility patch now queues up to 100 packets before Discord starts consuming them; a local timed simulation retained 100 queued packets after 10 seconds with no underruns. Listening in Discord after this change is pending.
- A later listening check still found persistent choppiness beginning 1–5 seconds after audio started. Every decoded Opus packet in that track was 20 ms and the largest was 639 bytes, below the sender buffer size. The Sonata patch now reports its queued frame count and UDP send/loss counters every 250 frames during playback so the next Discord test can distinguish sender starvation from packet loss. This diagnosis is pending a new playback log.
- The next Discord test identified sender starvation: the logged queue fell from 19 to 1 frames, while UDP reported zero lost packets. Between consecutive snapshots 7.7 seconds apart, the sender advanced 387 packets (about 50/s), but the Sonata producer added only 250 (about 32/s). On Windows the producer's 20 ms interval was effectively too slow for the sender. The patch now exposes the sender's queued frame count and refills to 100 frames on each producer tick. It also waits for the queued frames to drain before marking a track finished. In a local test with the producer forced to 31 ms and the sender at 20 ms, the queue held 98 frames after 12 seconds with zero empty reads. Discord listening after this fix is pending.
- Sonata's YouTube format selector used a bitrate comparison that could prefer AAC/MP4 over WebM/Opus, although this playback path uses a WebM/Opus demuxer. For `Me at the zoo`, that yielded zero audio frames and a false `finished` event. The compatibility patch now chooses the highest bitrate WebM/Opus format or reports no playable format. A timed local playback of the 19-second video sent and consumed all 951 Opus frames, reached zero queued frames, and then emitted `finished`.
- `InnerTubeClient.getVideo` now continues to another configured client profile if a profile returns metadata without a playable stream URL. A later local playback found a YouTube URL that answered HTTP 206 for the first byte range but HTTP 403 for a later range. The patch now reduces the range size from 1 MiB to 256 KiB and then 64 KiB before refreshing the URL. When refreshing midstream, it checks that the format ID, content length, and modification time match the already decoded bytes. With this patch, a full-length local test of the 172-second `double take` track sent and consumed all 8,597 packets at 50 packets/s, recorded zero empty reads, and emitted `finished` only after the final packet was consumed. Discord listening after this fix remains pending.
- Sonata's published 4.1.0 npm package lacks its source import map and only accepts WebSocket connections at `/`. `sonata/fix-package-imports.mjs` applies an idempotent local compatibility patch for Shoukaku's `/v4/websocket` path. The resolver also returns a v3-shaped result, which the adapter normalizes.
- Sonata 4.1.0 uses native WebSocket messages to start streaming; `SonataProvider` sends those messages while Shoukaku handles the Discord voice connection and Lavalink session. Upgrading Sonata requires checking these protocol differences again.
- Sonata's default legacy voice encryption was rejected by Discord with code 4016. The local config selects current AEAD modes. Its default silence frame is raw PCM sent as Opus and exceeded the packet buffer, so silence frames are disabled. The patch script also guards a reconnect attempt with a cleared voice endpoint to prevent a process crash after a failed voice handshake.
- In this Windows environment, `tsx` failed during initialization because `os.userInfo()` returned `ENOMEM`. Tests and command registration therefore run compiled JavaScript. `npm.cmd run build` followed by `npm.cmd start` is the verified bot startup path.
